# Project template

Each target application lives under `projects/<id>/` with a fixed layout enforced by `@qali/knowledge`.

## Scaffold

```bash
cp -R projects/_template projects/my-app
# Edit sources/project-context.md, sources/reference/*, sources/autonomy-policy.md
npm run project:validate -- projects/my-app
```

## Directory layout

```
projects/<id>/
├── execution-profile.json   # Environment label and deterministic execution policy
├── sources/                 # Governed truth (Qali-authored by default)
│   ├── project-context.md
│   ├── questions.md
│   ├── decisions.md
│   ├── autonomy-policy.md
│   └── reference/
│       ├── journeys.md
│       ├── risks.md
│       └── known-issues.md
├── observations/            # Evidenced behavior
│   ├── exploration.md
│   └── evidence/
├── derived/                 # Generated only — do not hand-edit
│   ├── scenarios/
│   │   ├── approved/
│   │   └── coverage-map.md
│   ├── reports/
│   ├── tasks/
│   ├── jobs/
│   └── workflow-state/
└── tests/
    ├── README.md
    └── generated/           # Specs from approved scenarios
```

## Ownership: source → observation → derived

| Class           | Examples                                         | Mutation rules                                           |
| --------------- | ------------------------------------------------ | -------------------------------------------------------- |
| **Source**      | Journeys, risks, decisions                       | Qali writes by default; humans may edit with provenance  |
| **Observation** | Exploration notes, screenshots, failure captures | Append-only with evidence links                          |
| **Derived**     | Scenarios, reports, coverage maps                | Regenerated by workflows; header marks generated content |
| **Tests**       | `*.spec.ts`                                      | Created only from `derived/scenarios/approved/*.md`      |

Manual edits to derived files or generated tests are overwritten on the next workflow run unless blocked by validation.

## Required files

`validateProjectDirectory()` checks:

- All paths in the template exist
- Generated files include the Qali provenance header
- Approved scenarios reference valid journeys
- No forbidden cross-class writes

## Environment configuration

Every target has `execution-profile.json`, and `projects/registry.json` is the only trusted map from a classified project ID to its root, GitHub Environment, Slack scope, publication target, enabled workflows, schedules, and active profile. The classifier never supplies those values.

Configure these names in the selected GitHub Environment; do not commit their values:

- `QALI_TARGET_BASE_URL`
- `QALI_ALLOWED_ORIGINS_JSON`
- `QALI_TEST_CREDENTIALS_JSON`
- `QALI_TEST_DATA_JSON`

Record non-secret context in `sources/project-context.md`:

- Base URL (production today for real targets)
- Test credentials (never commit secrets — use CI secrets)
- Browser matrix (Chromium default in MVP)

## Adding a real target

1. Scaffold from `_template`.
2. Add the canonical root and allowed Slack scope to `projects/registry.json`.
3. Set the active profile and create its named GitHub Environment.
4. Configure the four standard target variables/secrets in that Environment.
5. Fill project context and journeys.
6. Set autonomy mode in `sources/autonomy-policy.md`.
7. Run `onboard-project` through Slack or `npm run execute`.
8. Approve first scenarios, then generate and run suites.

No preview URL is required; document the exact URL Qali should hit.
